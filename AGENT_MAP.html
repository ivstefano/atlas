IRIS.ai: AI agent map

From the Strategy Day brainstorm, 12 May 2026: the diagram the room asked for: what context feeds which agent, and how the agents hand off. Read top to bottom: context flows down; corrections and new context flow back up (amber).

built live during the meeting, folded in from the Tactiq transcript as it was discussed. final: 817 blocks / ~76 min: meeting ended; covers the dev pipeline + 11 standalone agents.

3 · Dev agent pipeline - one feature, end to end · human gate only where it matters
triggered per feature: 1 starts when a feature is requested; 2→6 chain off it; 3↔4 self-loop until clean; 5 only on the items the agent flags high-risk.

impact ●●●build ◆

Fed → client-call transcripts (client describing their use case in their own words), business-meeting notes, prior specs.

impact ●●●build ◆◆

Fed → the spec from 1, repo dependency graph + architecture (from the code-intelligence agent), past similar plans.Could also weigh team availability / priorities: a "planner that knows the team".

3 Implementer agent

impact ●●●build ◆◆

Writes the code against the plan. First pass of agent iteration.

Fed → plan from 2, repo conventions / code style / git-commit format, the relevant client transcripts (so it builds what the client meant).Known weak spot: agents don't naturally make code reusable or human-readable: open question what to feed in to fix that.

4 Reviewer agent

impact ●●●build ◆ (exists)

Reviews the PR as a whole: already better than the in-editor agent (sees the full PR + last ~4 PRs, accumulates repo standards). "Some feedback, not human-level, doesn't remove your responsibility to go over almost everything": useful especially on the 2nd pass. Iterates with 3 on the bad stuff automatically. Reframe: its real job isn't reviewing this PR, it's building the knowledge file so the next review is better: each time a human has to add a comment the agent missed, that gap (how to structure things, what to look for) feeds back in.

Fed → the PR diff, repo standards KB, + proposal: meeting notes so it knows why conventions exist and what should be there (today it only sees what is there: and the sensitive review discussion happens outside the PR). Blocker surfaced: repos often have no architecture doc (e.g. A6 structural), so you can't tell the agent the intended design. Open Q: can an agent trace logic / run all scenarios in its head: even with full context? Reference: CodeRabbit / Travis-style AI reviewers were partly open-source; check what's in the bucket. auto-loop 3↔4
3 ↔ 4 iterate until only the important stuff is left for a human

Only the important things reach the human (more so the more "agent-first" we go: can't expect a human to read every line). Approve / edit / reject; bad outcomes feed back as corrections. Reachable from a phone (Layer 4) so the laptop isn't the bottleneck.

Repo-monitoring auto-fixer

impact ●●●build ◆◆

Hooked to monitoring: an alert comes in → agent triggered → analyzes it, maybe fixes it, opens a PR → goes through 4/5 above. Also picks up the small QA bugs Rossen files (~<1h each). If it gets stuck or has a question, it brings a human in. Hard prerequisite: strong automated test coverage (unit + integration; design the app to be mockable / testable): without it, agent fixes introduce regressions. ~90% of these bugs are catchable by tests. PR still reviewed

event-driven - monitoring alert webhook · new QA ticket from Rossen Assign it like a teammate (its own account, not just an API key) so its work is trackable; start it on the smallest issues (a single bug file, a known corner case) and widen from there.

Code-reuse / dedup agent

impact ●●●build ◆◆◆

Indexes all active repos. Tells you, at the moment you type in your IDE, what already exists and what to reuse: "I want to implement keyword extraction" → "that function already does it: modify these instead of implementing." Tackles the real cross-team duplication (e.g. SQL agents re-implementing the same code; the weekly "what is each team building" meetings exist partly because of this).

live in IDE - fires on keystroke / when you describe what you're about to build (LSP-style) Function-level indexing + docstring generation works well today on Python & JavaScript (most training data). The index itself re-runs on commit. Should also surface in-flight Asana tasks, not just code: "not in the codebase yet: Vladimir is on it."

impact ●●build ◆

Deploying is a whole day of retreatable steps: already written down in the repo README, just not automated. Most are scriptable; the rest need sanity checks (run the staging tests, confirm nothing's broken). The agent runs the steps, and if a command fails it fixes it instead of you.

Personal meeting assistant

impact ●●build ◆ (exists)

Team-orchestration agent (the AWS "agents observe the team" angle)

impact ●●build ◆◆◆

Watches how the team operates and builds a per-person profile (the "EU AI Act risk-classification" analogy applied to people). Then: suggests who should do which task, who should talk to whom, and facilitates the cross-team communication ("you need to talk to Martin: here's how to phrase it" given his profile). The bet: knowledge is globalized, but its interpretation is per-person; agents replace parts of a function, not people, and the weak spot they actually help with is team communication, not writing code.

passive - always on; profiles from meetings/PRs; nudges at task-assignment & handoff moments

Replaces clicking into each repo to check state. Stopgap until built: mark agent-reviewed PRs as draft (or rename them) so they filter cleanly in the existing PR list.

Personalization layer (cross-cutting)

impact ●●build ◆◆

Several of these agents: the dev assistant, the dedup agent, the meeting assistant, the team-orchestration agent: are tuned to how you personally like to work: give advice in your style, surface what you care about. "The future is personalization": one global knowledge base, per-person interpretation on top.

passive - always on; learns your style from every interaction, no explicit trigger
How to read this
  • The bet: the win isn't a smarter coding agent: it's unifying the information internally so every agent (and every human) has the right context. "Knowing what's developed / will be developed" matters; "knowing every step" doesn't, so repetitive meetings get summarized down to a context pack.
  • Lane 1 → 2: the only genuinely new capability is the synthesizer that re-projects all the scattered docs on demand. Transcripts/videos get transcribed + (BG → EN) translated + summarized into the store. Enable Google transcripts for internal meetings; external folks on Teams stay a friction point (Tactiq covers Teams, Gemini notes don't).
  • Lane 3: human-in-the-loop is on the spec and the important calls, not on every line. The agent classifies each action: auto-run / notify-me / needs my approval: and only the last reaches the phone, and never auto-proceeds on a timeout.
  • Cost caveat: coding agents are currently subsidized below true token cost. IRIS is fine for now (Hero on AWS startup credits) but the architecture should lean on self-hostable models where it can, so a price/policy change isn't fatal.
  • Known gaps to figure out: agents are bad at making code reusable / human-readable (they "don't care"): what do we feed them to fix that? Start the auto-fixer on the smallest issues (a single bug file, a known corner case) and widen. And: pre-commit hooks (deterministic scripts at fixed points in the agent lifecycle: format, lint, tests) guarantee correctness before a commit lands, since you can't expect a human to read every line in an agent-first workflow.
